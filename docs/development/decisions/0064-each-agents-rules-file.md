# 0064: Each agent's rules file

**Built:** yes, except: asking where lines setup didn't write go, the always-on blocks of the
skills, and reporting an `AGENTS.override.md`. Until setup asks, it leaves a file in its way, or
one with lines it didn't write, as it is, and reports it on every sync, after a no as well.

**Decision:** every agent gets its always-on rules as one file that setup writes in the agent's
own folder: each Codex home's `AGENTS.md`, and `dev-home-rules.md` in each Claude Code folder's
`rules\`, in place of the two links there before. Setup owns that file by name, writes it on every
run, and removes it when the end user answers no for that folder. The file joins the operating
rules, with the always-on blocks of the skills added for that agent, and the end user's rules for
that agent on that PC
([0065: Where end users' rules live](0065-where-end-users-rules-live.md)).
Decided by the developer on 2026-10-17 and 2026-10-18, and changed on 2026-10-22 (the file's
name) and 2026-10-23 (the headings moved lines keep).

- **No generated file carries a note** such as "Generated by ... Do not edit this copy": not the
  generated `SKILL.md` files, the generated operating rules, each Codex home's `AGENTS.md`, nor
  dev-home's per-PC `AGENTS.md` and `CLAUDE.md`. Setup tells its own file from an end user's by
  the copy below, not by a note. The file in a Claude Code folder's `rules\` starts with
  `dev-home-`, as the links there did, since nothing in that folder says which repo a file comes
  from, and a plain `rules.md` could clash with one of the end user's own.
- **Setup keeps a copy of what it last wrote,** on that PC only, in a folder of
  `internal/.generated/` such as `last-written/`. Each run:
  1. No file: write it.
  2. It matches the copy: overwrite it with the current rules.
  3. It differs from the copy: ask where the lines that aren't in the copy go, then overwrite; or
     just overwrite, when nothing was added.
  4. No copy, and it doesn't start with the operating rules' heading, "Private repo: dev-home
     (rules loaded)", kept first per [skills.md](../skills.md): ask where the whole file's rules
     go, as at a takeover, below.
  5. No copy, and it starts with that heading, as setup's output from another PC or a lost copy
     would: compare it with the new version, overwrite when they match, and otherwise ask about
     the lines that differ. They may be setup's own older text, so dropping them is an answer.
- **Taking over a file in the way.** At the end user's yes for a Codex home, setup gathers the
  home's existing `AGENTS.md`; in a Claude Code folder, only a file already at setup's own path.
  It shows the content and asks where it goes: every agent on every PC, that agent on every PC,
  every agent on this PC, that agent on this PC, or drop it. It puts each file it moves, as a file
  of its own, in that level's `mine/`, commits and pushes, only then removes the originals, and
  owns the file from then on ([0066: Notes in rule files](0066-notes-in-rule-files.md) has how
  moved files are named and marked). An `AGENTS.override.md` is left alone and reported on every
  sync: Codex documents it as a temporary switch that replaces `AGENTS.md`.
- **Lines added to setup's file later,** in either agent, get the same question, at the next run
  at a console or through `/dev-home configure`. The file they move into keeps the headings they
  sat under in setup's file, so joining puts them back in the same section. A line under one of
  the operating rules' top-level headings keeps none of its headings, and joining puts it under
  `# My rules`. Lines in a code block keep its fence.
- **A run that can't ask,** a quiet sync at the start of a skill command, puts those lines in
  `rules/pcs/<pc>/<agent>/unanswered/` in dev-home, commits them, joins them for that agent on that
  PC after `mine/`, and names them in a `NEW` line. Answering through `/dev-home configure` or a run
  at a console moves the file into the `mine/` picked, or drops it. The folder is the record:
  moving a file out by hand counts as answering. Setup owns the folder, and writes the agent's
  file right away either way. Dropped text goes to the Recycle Bin
  ([0069: Dropped text](0069-dropped-text.md)).
- **Claude Code's other files are left alone:** setup never takes over `~/.claude/CLAUDE.md` or
  the other files in a Claude Code folder's `rules\`, nor checks them later.
- **A no for an agent's folder:** setup first saves any lines added to its file, as on any run,
  then removes only what it owns there: its rules file, its last-written copy, and the links and
  settings lines it already removes
  ([0054: Removing what setup set up](0054-removing-what-setup-set-up.md)).
  It says so in one line, noting that the rules are still in dev-home. Nothing in dev-home changes,
  and setup stops creating `my-rules.md` for that agent on this PC. A later yes writes setup's file
  again from dev-home, with nothing to take over.

**Why:**

- One way for every agent, and rules for one agent or one PC load only where they apply. It ends
  a mismatch: Claude Code loads every `.md` in the linked global rules folder, while Codex gets
  only `global-rules.md`, joined into its `AGENTS.md`.
- A file written in the agent's folder works where a link may not. Claude Code's memory docs
  (read 2026-10-18) say Cowork, Claude Code inside the desktop app, skips "a symlinked
  `~/.claude/rules/` directory or rule file that points outside the working directory". Whether it
  treats a Windows junction as such a link is untested. dev-home can also sit on a network share.
  No reason for links over copies was ever recorded, and copying costs well under a millisecond.
- The last-written copy shows exactly what was added, where a hash only shows that something
  changed, so no hand edit is lost. The full-text comparison took 0.07 ms on a normal run,
  measured 2026-10-18 on a fast developer PC. Finding the added lines took at most 54 ms in files
  up to 134 KiB, from one line added to every line changed, measured 2026-10-23 on the same kind
  of PC. It compares lines as patience diff does, since Python's difflib alone took 76 seconds on
  a 93 KiB file whose rules all changed: it pairs each of its thousands of blank lines with every
  other. The heading check keeps setup's own output from another PC out of `mine/`.
- No notes: a note that differs by agent isn't consistent; end users know where their rules go,
  since the operating rules' last line names the folder; and an agent's own needs are met by
  joining rules. Measured 2026-09-30: Claude Code hides HTML comments in rules files and
  `CLAUDE.md`, but not in a `SKILL.md` body; Codex shows them everywhere; neither shows a skill's
  frontmatter. So a note cost about 50 tokens per skill load, and per Codex session.
- Keeping the headings: a line such as "- Same for commit messages." means something only under
  its heading, and joining combines matching headings, so the moved lines land where they were.
  The operating rules' headings aren't the end user's, and one in their rules would start a
  second section that reads like the operating rules (the developer, 2026-10-23).
- Asking where moved rules go keeps an end user's rules where they meant them. A question can
  wait days, so on a quiet sync the lines wait in `unanswered/`, still joined, so the agent keeps
  what it had, and `mine/` stays the end user's.
- Leaving Claude Code's other files alone keeps its own features working as its docs describe:
  `/memory` creates and edits `~/.claude/CLAUDE.md`, and a rule with `paths:` frontmatter loads
  only for matching files, which a joined file can't keep. It also matches Codex, whose only
  other file, `AGENTS.override.md`, is left alone too.
- On a no, the end user's content stays in dev-home: putting it back is "probably a bad idea to do
  automatically, if at all" (the developer).

**Costs:** a hand edit to a rule reaches agents at the next setup run, which comes at the start of
nearly every skill command; a copy in each Claude Code folder; a reserved file name; a stale copy
if a removal fails; churn for end users who sync `~/.claude` themselves; and rules kept in Claude
Code's other files reach only Claude Code, on that PC and account.

chezmoi, too, records what it last wrote and reports a file that differs. Where the copy lives,
the five cases, and the questions are dev-home-toolkit's own design.

**Options set aside:**

- A note only where each agent hides it (a YAML comment in a skill's frontmatter, an HTML comment
  in Claude Code's rules, none for Codex): it differs by agent, and rests on measurements to redo
  for each. Keeping the notes; researching other agents first.
- Keeping the links; one link to a file in `internal/.generated/` (one file per PC, recognized by
  its target, but likely nothing loads in Cowork); testing Cowork first.
- Overwriting hand edits in Claude Code's file; a hash in place of the copy (it can't find added
  lines, and comparing with the new version brings back rules deleted on another PC); rebuilding
  from dev-home's history (git calls, and settings and versions also shape what was written);
  markers in the file (Codex loads them); the copy beside the agent's file (Claude Code loads any
  `.md` in `rules\`), in a new `internal/.state/`, or in the operating system's app folder.
- Moving content without asking; refusing to set up a folder that has a file in the way, as
  before; setup owning `AGENTS.override.md` and leaving `AGENTS.md` to the end user (the developer
  turned down both).
- Taking over all of Claude Code's other files (`/memory` would open an empty file after each
  move, and scoped rules would need extra files); a one-time offer to move them; taking over all
  but scoped files (an exception to the rule).
- Offering only three of the four levels at a takeover, leaving out every agent on this PC: a rule
  true for every agent but only on one PC, such as where that PC keeps its projects, would have to
  be moved there by hand.
- Removing or overwriting lines added later on every run; leaving them and reporting them.
- Moving added lines without their headings: joining would put them at the top of `# My rules`,
  outside the heading they had.
- Finding added lines with Python's difflib alone: minutes on a large file whose lines repeat,
  such as blank lines and code fences. With its `autojunk`, which skips lines that repeat, it's
  fast, but a skipped line can never match, so a code fence could move as if it were added.
- Leaving the agent's file alone until a question is answered; waiting files in `mine/`; one
  `rules/unanswered/`; not joining waiting files.
- On a no, offering to leave the rules in the agent's folder as a plain file: a later yes would
  take it over again.

**Look again if:** Cowork is found to load linked rules folders, or either agent gains a way to
load several global rules files.
